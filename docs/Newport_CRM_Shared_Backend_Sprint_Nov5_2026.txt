PART I — SHARED STORAGE & SYNCHRONIZATION (HIGHEST PRIORITY)

1. IDENTITY, AUTHORIZATION & PRIVACY BOUNDARIES
- Maintain existing Microsoft authentication and Graph permissions. Validate identity on the trusted backend for every API call (verify tokens, issuer/audience/signature/expiry as appropriate), rather than trusting editable email/profile fields or frontend-controlled roles. Use stable Microsoft tenant/account identity, not a changeable contact email, as user ID.
- Only users actually authorized for Newport's CRM workspace may access shared company records; don't assume any Microsoft/outlook.com account in the world may access. Document secure tenant/workspace onboarding and membership enforcement. No elaborate admin-vs-standard editing hierarchy is requested, but membership/auth boundaries must be real.
- Scope shared company records to the correct Newport organization/workspace. Design for future organizations only if it doesn't complicate this sprint.
- Meeting data is USER-PRIVATE: an Outlook event's full details, participant list where private, meeting history record, transcription text/VTT, Gemini summaries, proposed follow-ups before creation, recording URL, and private notes must only be read/written by their owning signed-in user. A meeting linked to a shared opportunity does NOT make it public. On a full Opportunity Profile > Meetings, query by BOTH opportunity ID AND current user identity. Don't expose another user's private meetings in global searches, exports, activity payloads, notifications, backend queries or shared audit logs. General shared task records CREATED from AI meeting suggestions can be shared once explicitly saved as Tasks, but must not leak raw private transcripts or private notes.
- Outlook Email and Calendar should remain scoped to the signed-in account using the current integration. Do not pool or share inbox/calendar across staff. Keep Microsoft login screen unchanged.
- Account/device isolation of Meetings survives logging in from another device as the SAME user: the user sees their own saved meeting history on both devices, not anyone else's.

2. PERSISTENT DATA INVENTORY AND SCHEMA
At minimum make durable structured records and relations for:
- Organizations/workspace memberships/identities (as needed).
- Opportunities and their status, acquisition stage, financials (NWP, net revenue, PF EBITDA), source, diligence/company fields, created/updated/legally-closed dates and historical transitions.
- Deal Leads (stable IDs, full name, title, contact email, phone, Active/Inactive, identity link if available), primary/additional opportunity assignments and legacy preserved attribution.
- Tasks & Follow-Ups with title/action, owner association, opportunity ID, priority A/B/C, status, due date, completion date, historical due-date changes, archived state and restoration history. Preserve tasks belonging to non-Active/Pending opportunities without showing them in active list.
- Relationships/contacts with many-to-many linked opportunities.
- Documents metadata, type (NDA, LOI, CIM, IOI, DA, FA, custom), confidentiality/status, link to opportunity, actual encrypted/private file storage reference, version/replace/delete state.
- Shared immutable/auditable activity event history and user-visible archive/restore state; logical archive of feed entries must not delete underlying audit evidence.
- User-owned CRM meeting records, link to opportunity, participant/contact links as applicable, private VTT and recording URLs, AI summaries/actions and note content. No cross-user access.
- Report inputs and preserved event history for created/closed/weighted pipeline, completed provisional 24-hour rule, missed deadlines and current/history filters. Reports must calculate from actual shared records; don't hardcode totals.
Use stable IDs and referential integrity. Schema version, timestamps UTC plus appropriate local-date display, reliable migrations, deduplication and deletion semantics are mandatory.

3. SAFE MIGRATION FROM LOCAL STORAGE
- Inventory localStorage/IndexedDB/cache/local backups as used in actual repository. Make a one-time, user-visible and ideally opt-in migration/import flow for legitimate local records. Do NOT simply replace storage and make existing data disappear.
- Back up existing local data BEFORE migration; preserve ability to export/download database backup. Document whether other devices may contain divergent local datasets and how to import/reconcile them without data loss or duplicates.
- Detect duplicates using stable IDs and content/version data; never overwrite newer shared data with stale local data silently. Keep immutable original timestamps where present. Preserve real uploaded file bytes; verify document downloads after migration, including any blobs currently stored in browser storage. An empty backend is not a reason to seed over users' existing records.
- Plan rollback/recovery for failures: transaction or safe batch, progress/error, ability to retry, no partial-deletion of local data. Avoid global auto-migration of someone else's private meetings to public tables.
- After successful migration, treat the backend as authoritative; local state can be a cache only, not a divergent independent system. Clearly label offline/failed-sync edits rather than pretending they're shared.

4. CROSS-DEVICE LIVE/NEAR-REAL-TIME SYNCHRONIZATION
- Shared changes in Opportunities, Tasks, Relationships, Deal Leads, Documents, and activity feed should propagate to other signed-in employees/devices. Aim for near-real-time subscription/WebSocket/SSE, or dependable polling with an explicit bound/documented latency and reconnect behavior if deployment constraints dictate. Cross-tab refresh also works.
- Ensure one change updates Dashboard counts, Pipeline, Needs Attention, This Week's Priorities, task links, Deal Lead cards, Opportunity Profiles, Documents, Reports and Recent Activity consistently for all users. The same linked item must have ONE source of truth. Restore task and delete lead actions must also propagate.
- On collisions/concurrent edits, implement version/revision/ETag/optimistic concurrency or transactional merge strategy and tell users when changes conflict. Do NOT silently last-write-wins and overwrite another person's work without visibility. Support field-aware merge when safe, conflict notification otherwise.
- On login/new device, fetch all authorized shared data from server; on sign-out, clear private in-memory caches/tokens and display correct account data. A device must not show another employee's private meetings after account switch.
- Backend-driven audit event includes actor, time, entity, action and relevant changed fields, subject to privacy/redaction. Non-editable audit trail remains even if activity UI entry is archived. Feed archiving must be recoverable and not corrupt reports. User name must match actual authenticated identity.
- Treat the database as the source of truth for new report figures and export data. Prevent duplicate financial counting for one opportunity with primary + additional Deal Leads. Preserve completed-deal 24-hour reporting treatment and real legal completion date; handle reversals.

PART II — SPECIFIC USER-REQUESTED FIXES (DO NOT OMIT)

8. DEAL LEADS — REMOVE ADMIN/SELF-ONLY RESTRICTIONS
- Remove UI restrictions implying only 'my profile' or an administrator can edit someone else's Deal Lead. For authorized Newport CRM users, all Deal Lead profiles can be viewed/edited, and new leads can be created. No admin/standard labels or User Management page are needed for ordinary record editing.
- All users can edit another Deal Lead's full name, title, editable contact email, phone, linked opportunities and Active/Inactive status. Microsoft sign-in identity is a stable association distinct from editable contact email. An employee's edit to a lead's contact email must not change whose Microsoft account that lead belongs to.
- Add a clearly labeled ACTIVE / INACTIVE selector in the Deal Lead right-side editor (near linked opportunities or in a logical position before Save). Any CRM user may change it. Only Save commits; audit actor and before/after. Update card/status filters and available assignment dropdowns. Inactive leads are not offered as NEW primary/additional Deal Lead or new Task Owner; pre-existing references remain visible. Deactivation must NOT sign anyone out or remove their CRM access.
- Eliminate hardcoded Dennis/Mary lists and automatic addition of every Microsoft login as a lead. The roster is explicit. Duplicate prevention should rely on lead ID / linked identity, not name string; if name edited, task/lead assignments still resolve.

9. DEAL LEAD DELETION — FINAL RULE (OVERRIDES EARLIER PROPOSALS)
- All authorized CRM users may request Delete Deal Lead, with a confirmation. The Delete control must exist in the existing Deal Lead right drawer, appropriate to its dark navy style and other destructive actions.
- PERMANENT DELETE is allowed ONLY when Deal Lead is genuinely UNUSED: no linked opportunities as primary/additional, no Task Owner references, no required historical financial/reporting references and no other persisted dependencies. Check on trusted backend and block/reject deletion when dependencies exist, even if UI was stale. Warn with specific counts and path to deactivate/reassign.
- For USED Deal Leads, require deactivation OR appropriate reassignment/cleanup of dependencies first; preservation of historical references is mandatory. Deactivation is an alternative to removing a used lead; it should remain in the database and historic views. Do NOT automatically unassign Active/Pending deals or permanently erase used leads on Delete. This final requirement supersedes an earlier suggestion to automatically unassign on deletion.
- For UNUSED lead deletion, optionally provide a short Undo toast (e.g., 10 seconds) backed by a recoverable soft-delete/tombstone window, but never claim a truly irreversible hard-delete can be undone. Backend must handle race conditions. Log deletion/restoration in audit history. If user declines in confirmation, change nothing.
- Active/Inactive and Delete are distinct. Never cascade-delete acquisitions, tasks, documents or reports to remove a lead. If the deleted lead is the currently signed-in user's linked roster entry, keep their Microsoft access working.
